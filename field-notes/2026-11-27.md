# Two missing gaskets per kit

In this fictional 30-kit run, the proposed import would put 60 gaskets on the picking list. The approved bill of materials calls for 120. Both files name the same kit and gasket, so checking whether the SKUs exist would miss the 60-piece shortfall.

In the Znode example, proposal record 2 links kit `KIT-710` to gasket `GSK-004`. The proposed `Quantity` is 2 gaskets per kit. The approved quantity is 4. Multiplying the difference by the run size gives `(4 − 2) × 30 = 60` missing gaskets if the proposed quantity drives picking. [Proposed associations](../examples/znode-bundle-associations/proposed.csv) · [Approved bill](../examples/znode-bundle-associations/approved-bom.csv)

## Reproduce the check

Run the checker from the repository root.

```sh
python examples/znode-bundle-associations/preflight.py
```

Look for `KIT-710,GSK-004` in the output. Record 2 reports a proposed quantity of 2, an approved quantity of 4, and a decision of `REVIEW`. The full file yields two matches and six rows for review. Use the parent **and** the child SKU to locate the proposed correction. The same kit legitimately appears on several rows. [Expected review CSV](../examples/znode-bundle-associations/expected-review.csv)

To test the correction, save a copy of `proposed.csv` as `trial.csv` in the repository root. On the `KIT-710,GSK-004` row, change only the final field, `Quantity`, from 2 to 4. Leave `DisplayOrder` at 2. Run the checker on your copy.

```sh
python examples/znode-bundle-associations/preflight.py --proposed trial.csv
```

Record 2 now reads `MATCH`, and five other rows still need review. For a live import, confirm the kit revision and whether quantities are in pieces, packs or cases with the bill owner before approving the change.
